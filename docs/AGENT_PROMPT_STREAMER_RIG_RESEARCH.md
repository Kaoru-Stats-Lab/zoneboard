## 何を決めるか

ZoneBoard（ブラウザ戦術ボード · OBS 窓キャプチャ）の **局面取込（動画→PNG · Homography）** が、配信中でも机を壊さないための **設計下限スペックと机レイアウト**を、証拠付きで置く。

特に:

1. **地域** — 日本だけに閉じない（EN 圏 · EU · LATAM · 可能なら他）  
2. **競技** — **メインはサッカー／フットボール**。あわせて **バスケ · バレー · その他**（アメフト · ラグビー · アイスホッケー · eSports 等）の配信机の差  
3. **ZB の他スポーツ展開** — [`SPORTS_SCOPE.md`](SPORTS_SCOPE.md) の v1（サカ/バス/バレ）と Later を見据え、**負荷プロファイルが同じ机か違う机か**

「推奨ゲーミング PC ガイド」だけを配信者分布とみなさない。**ウォッチアロング / 戦術解説 / スポーツ実況**の机を優先する。

## ZoneBoard が知りたいこと（なぜこの調査か）

局面取込のハード境界（既存）:

- 処理は **ローカル · ブラウザメモリ**  
- **OBS が掴むボード窓の配信が途切れない**  
- 想定机は **PC1台 · マルチモニター** が主（仮）  
- 設計下限は **16GB 級でも死なない**（仮 · [`BROADCAST_CAPTURE_IMPORT_RESEARCH.md`](BROADCAST_CAPTURE_IMPORT_RESEARCH.md) §3e）

**この仮を残すか・引き上げる/下げるか・競技別に分岐するか**を決める材料が欲しい。

### スポーツ配信の負荷はゲーム実況と違う（仮説。検証せよ）

| 型 | 典型負荷 |
|----|----------|
| **ゲーム実況** | AAA / 競技タイトル描画 + OBS エンコード |
| **スポーツ watchalong / 解説** | **試合映像のデコード**（ブラウザ or 再生ソフト）+ OBS + **戦術ボード（ZB）** + チャット。GPU ゲーム負荷は軽いことが多いが **動画デコード + 複数ブラウザ**が重い |

局面取込の動画シークは、後者の机に **さらにデコード負荷**を足す。ゲーム実況ガイドの「RTX 5070 + 32GB」をそのまま下限にしないこと。

## 調査すべき問い（すべてに答える）

### A. データがあるか

1. 配信者の **RAM / CPU / GPU（NVENC 有無）/ モニター枚数 / 1PC vs 2PC** について、**定量調査**はあるか（平台 · メーカー · 学術 · コミュニティ）。年次と n を書く。  
2. なければ **使える proxy** を列挙（BTO 売れ筋、OBS フォーラム、VTuber/YouTuber の機材公開、Twitch/YouTube クリエイター調査、Reddit、Discord アンケート等）。各 proxy のバイアスを1行。

### B. 地域

3. **日本** — ゲーム配信 / VTuber / スポーツ実況の机。16GB 残存率、デュアルモニタ常識度、ノート配信の割合（分かる範囲）。  
4. **英語圏（US/UK/AU 等）** — football / soccer watchalong、NFL reaction、NBA の典型。  
5. **EU · LATAM · その他** — 見つかった範囲。データが薄い地域は「薄い」と書く。  
6. 地域差で **ZB の設計下限を分ける必要があるか**（1つの全球下限でよいか）。

### C. 競技別（サッカー主 · 他も）

各競技について、分かる範囲で表にする: **机の形 · 同時アプリ · エンコード解像度 · 1PC/2PC · ZB 局面取込との相性（配信中抽出の危険度）**。

7. **サッカー / football（協会）** — watchalong、戦術チャンネル、マッチデー実況。メイン。  
8. **バスケ** — NBA reaction / 解説。映像解像度・テンポの差。  
9. **バレー** — 国際大会解説 · 国内配信。  
10. **Later 候補** — アメフト · ラグビー · アイスホッケー · ハンド · 野球（ボード適性は別）· **eSports**（マップ差し替え展開を見据え、机はゲーム実況に近いか）。  
11. **競技間でハード境界を変えるべきか** — 1本の帯 A で足りるか、スポーツ解説機 vs ゲーム実況機で分岐か。

### D. モニターと窓

12. **1 / 2 / 3+ モニター**の実務上の分布（定量がなければ質的）。  
13. 典型レイアウト例（試合 | OBS/チャット | ボード）。ZB を **OBS 窓キャプチャ専用モニター**に置く割合の仮説。  
14. **1モニターのみ**の配信者比率の見当。局面取込 UX（別タブ強制）への影響。

### E. スペック帯の再提案

15. 既存の仮帯を改訂せよ:

| 帯 | 現行仮（§3e） | 調査後の提案 | 根拠 |
|----|---------------|--------------|------|
| A 設計下限 | 6–8コア · **16GB** · iGPU/エントリ · 1080p | ? | |
| B 主ペルソナ | dGPU · NVENC · 16GB+ · デュアル+ | ? | |
| C 余裕 | 32GB · 中高 dGPU · 3モニタ | ? | |

16. **RAM を 16GB のまま下限にするか、24/32GB に上げるか。** ウォッチアロング机でのブラウザ多重を根拠に。  
17. **配信中コマ抜き**を帯 A で許す条件（別タブ必須 · 解像度上限 · 配信前のみ 等）。

### F. ZB 他スポーツ展開への含意

18. サカで決めた下限がバス/バレにそのまま使えるか。  
19. eSports 展開時に「ゲーム実況機」向けの **別ハード境界**が必要か。  
20. プロダクトへの推奨を3行: 全球1下限 / スポーツ解説向け1下限 / モード別、など。

### G. 決定メモ

21. **確信度付き**で: 帯 A/B/C の改訂案 · モニター想定 · 1PC 前提の維持可否。  
22. **追加でやる一次調査**（配信者5人インタビュー項目、匿名フォーム質問票）を提案。Web だけでは足りない穴を書く。
